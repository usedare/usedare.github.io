## 实验目标

本实验围绕 Jekyll 静态网站生成器展开，目标包括：

- 理解 Jekyll、Markdown、静态网站生成和 GitHub Pages 部署流程。
- 使用 Jekyll 搭建个人博客，并保留代码、命令行和网页截图证据。
- 围绕专题网站完成本地运行、页面展示和过程总结。
- 说明 Jekyll 的适用场景与局限，体现规范表达和独立思考。

## 小组专题网站展示

专题网站采用“课程实验档案”的组织方式，将实验目标、运行步骤、截图证据和思考题集中到一个页面中，便于教师检查和小组成员协作补充。

核心页面结构：

1. 实验目标：说明 Jekyll 与静态网页技术的学习目标。
2. 个人博客：展示站点结构、文章系统和 GitHub Pages 发布路径。
3. 本地运行：记录 Docker 运行命令与访问地址。
4. 过程证据：列出应提交的代码截图、命令行截图和网页截图。
5. 思考总结：说明 Jekyll 不适合做什么，以及静态网站开发中的合规要求。

## 本地运行步骤

```bash
git clone git@github.com:usedare/usedare.github.io.git
cd usedare.github.io
docker compose up --build
```

浏览器访问：

```text
http://localhost:4000
http://localhost:4000/topics/jekyll-experiment/
```

如果本机已经安装 Ruby，也可以使用：

```bash
bundle install
bundle exec jekyll serve
```

## Jekyll 的适用场景

Jekyll 适合内容更新频率适中、页面结构稳定、以阅读和展示为主的网站，例如个人博客、课程实验记录、项目文档、作品集和社团专题页。它生成纯静态文件，部署简单，访问速度快，安全风险相对较低。

## Jekyll 不适合做什么

Jekyll 不适合承担强后端逻辑的网站：

- 不适合实时聊天、在线协同编辑等强实时应用。
- 不适合订单、支付、库存、考试提交等强事务系统。
- 不适合依赖复杂权限、数据库写入和后台审批流的业务系统。
- 不适合非技术人员高频通过后台管理海量内容的场景。

原因在于 Jekyll 的构建结果是静态文件，它没有内置数据库、用户认证、服务端 API 和事务处理能力。若强行实现这些功能，需要额外接入后端服务或第三方平台。

## 总结与思政体会

这次实验让我认识到，静态网站开发不只是“把页面做出来”，还包括内容组织、版本管理、部署流程、证据留存和规范表达。使用 Git 记录过程，使用 Markdown 书写文章，使用 GitHub Pages 发布页面，能够让学习结果长期可追溯。

在内容合规方面，实验网页应坚持真实记录：截图来自实际运行，素材使用注明来源，代码引用遵守开源协议，小组协作时明确分工与贡献。技术能力应与诚信意识、协作意识和社会责任结合起来，才能形成可靠、可复现、可持续的工程实践。
